# J4 — `@ambreia/iso` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** sortir le moteur de room (`room/` + le rendu de `habbo/room`) dans un paquet `@ambreia/iso` qui charge et affiche une room sans session de jeu, avec le rendu des mobis et celui des effets en modules séparés qu'un hôte enregistre ou non.

**Architecture:** comme J3, on coupe d'abord les liens du rendu vers le jeu, on les remplace par des options et des registres, puis on déplace par `move-modules`. `RoomEngine` (10 200 lignes) et `RoomMessageHandler` restent au moteur : c'est la colle avec la session et le réseau. `iso` expose une entrée hors session, `IsoStage`, tirée de la pile que l'imager monte déjà (`vortex-imager/src/room/RoomStack.ts`, `RoomRenderService.ts`). Le moteur, l'imager, le bac à sable et l'éditeur de cartes passent tous par elle.

**Tech Stack :** TypeScript, PixiJS v8, pnpm workspace, `node:test` + `tsx`, `move-modules.mjs`.

**Spec :** `docs/superpowers/specs/2026-10-07-client-architecture-design.md` (§3, §9 J4, §11, §12 n° 4). Entrée de l'éditeur de cartes : mémoire `j4-map-editor-input` et `../vortex-rpg-emulator/schemas/zone.schema.json`.

## Global Constraints

- Les moteurs n'importent jamais `kernel`, `protocol`, `game` ni le client (spec §3, règle 1).
- `iso` PEUT dépendre d'`avatar` ; l'inverse est interdit (spec §3, règle 2). `iso` dépend de `@ambreia/common` et `@ambreia/avatar` seulement (pas `ui`, pas `net`).
- Fin de jalon : le client compile, démarre et on entre dans une room (§9).
- Preuve J4 : bac à sable `iso` qui charge une room ; l'imager rend une room sans faux `Vortex.ts` (§9, §11).
- Commits par chemin uniquement (`git commit -m … -- <chemins>`), jamais `git commit` nu.
- Traces `// AS3:` conservées sur tout membre déplacé ; `dispose()` en dernier avec retour anticipé.
- Boucles de rendu : aucune allocation par frame.

- **D4 — Découpe demandée par le propriétaire (2026-10-07) : mobis et effets à part.** `iso` a quatre modules, chacun avec sa fonction d'enregistrement :

  | Module | Contenu | Enregistrement |
  |---|---|---|
  | `src/` (noyau) | `room/` du moteur : gestionnaire, instances, objets, renderer, événements | — |
  | `src/scene/` | `habbo/room` hors mobis/avatars/effets : chargeur de contenu, fabriques, renderer Habbo, plans, room, curseur de case, flèche de sélection, données de plans | `registerScene(registries)` |
  | `src/furniture/` | logiques et visualisations de mobis, données de furnidata (`IFurnitureData`, `FurnitureData`, `FurnitureDataParser`) | `registerFurniture(registries)` |
  | `src/avatar/` | logiques avatar/animal/`MovingObjectLogic`, `AvatarVisualization`, visualisation d'animal | `registerAvatars(registries)` |
  | `src/effects/` | additions d'avatar (bulles, cœurs, Z, expressions, statut de guide), systèmes de particules, feux d'artifice (y compris emballés) | `registerEffects(registries)` |

  Les effets d'avatar (danse, effets portés) restent dans `@ambreia/avatar`, qui les rend déjà.
  - `AvatarVisualization` ne construit plus ses additions : elle passe par un `IAvatarAdditionFactory` (statique `AvatarVisualization.additions`, `null` par défaut). Sans effets, un avatar n'a pas de bulles et ne plante pas.
  `registerFurniture` enregistre `furniture_fireworks` et `furniture_gift_wrapped_fireworks` avec la visualisation animée (resp. emballée) ; `registerEffects`, appelé après, les remplace par les visualisations à particules. Sans effets : le mobi s'affiche, sans ses particules.

      addItem(roomId: string, item: IIsoFloorItem | IIsoWallItem): Promise<void>;   // incremental edits: one stroke = one call, no reload
      updateItem(roomId: string, item: IIsoFloorItem | IIsoWallItem): Promise<void>;
      removeItem(roomId: string, id: string | number): void;
      setTile(roomId: string, x: number, y: number, tile: IIsoTile): void;          // rebuilds the floor planes only
      update(deltaMs: number): void;
      disposeRoom(roomId: string): void;

## Review Focus

1. **Un type de mobi ou de logique disparaît** (registre non rempli, ou enregistré par le mauvais module) → mobi invisible ou inerte en room. Attendu : tous les types d'aujourd'hui se créent avec les quatre modules. Pin : Task 3, test qui compare `types()` à la liste relevée avant le changement.
2. **L'hôte n'enregistre pas les effets** → un avatar inactif, qui tape ou en sourdine plante (addition `null`), ou un feu d'artifice ne s'affiche plus du tout. Attendu : pas de bulle et pas de particules, mais avatar et mobi visibles. Pin : Task 4, tests « sans effets ».
3. **L'extracteur de textures n'est pas posé** (imager, bac à sable sans renderer) → exception là où le shim renvoyait une erreur attrapée. Attendu : `null`, comme avant. Pin : Task 1, test `extractCanvas` sans extracteur.
4. **Ordre de démarrage du DI** : `RoomEngine` reçoit `IID_RoomManager` avant que les fabriques soient posées (voir le commentaire de `RoomManager.ts:154-167`) → room vide. Attendu : identique. Pin : Task 2, test d'`attachInstance` + parcours en direct (Task 8).
5. **Données de l'éditeur hors bornes** (`length` > 64, `rotation` hors 0/2/4/6, mur `side` inconnu, porte hors grille) → exception dans le parseur de plans. Attendu : erreur nommée par `loadRoom`, rien d'affiché à moitié. Pin : Task 6, tests de validation.
