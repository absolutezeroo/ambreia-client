# J5 — `@ambreia/kernel` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** un paquet `@ambreia/kernel` qui porte le DI, une configuration typée par Zod (sections, `enabled`, `legacy`) et les features déclarées (`defineFeature`, `FEATURES`), et qui démarre le client à la place de `VortexMain.prepareCore`, à l'identique.

**Architecture:** le DI (`core/runtime`) déménage tel quel dans le paquet. La configuration est chargée une fois, validée par Zod et figée avant toute feature. Ses sources, dans l'ordre : défauts des schémas, `config.json` du déploiement, paramètres d'URL. La section `app` (serveur, liens) remplace la logique d'hôte d'`index.html`. La section `legacy` (`clé: valeur`) alimente l'actuel `HabboConfigurationManager`, qui continue de télécharger `external_variables` et sert les ~270 `getProperty` : c'est l'adaptateur de migration du §5. Les douze managers de `prepareCore` deviennent des features ; le kernel les crée dans l'ordre de `FEATURES` et refuse de démarrer quand une dépendance obligatoire n'a pas de fournisseur.

**Tech Stack :** TypeScript, Zod (nouvelle dépendance, admise par la spec §10), pnpm workspace, `node:test` + `tsx`.

**Spec :** `docs/superpowers/specs/2026-10-07-client-architecture-design.md` (§3, §4, §5, §9 J5, §11).

## Global Constraints

- Les moteurs (`common`, `net`, `avatar`, `iso`, `ui`) n'importent jamais `kernel` (spec §3, règle 1). Le `kernel` n'importe que `@ambreia/common`, `zod` et `eventemitter3`.
- Config « typée, chargée une seule fois, validée, puis figée » ; trois sources dans l'ordre : défauts → `config.json` → paramètres d'URL (§5.4).
- Config invalide = démarrage arrêté sur un écran listant les champs fautifs (§5.5) ; section inconnue = avertissement (§5.6).
- Chaque section a un `enabled` (vrai par défaut) ; une feature active qui dépend obligatoirement d'une feature désactivée fait échouer le démarrage avec un message clair (§5.3, §4).
- Preuve J5 : `VortexMain.prepareCore` remplacé, démarrage identique (§9). Tests §11 : config invalide → erreur listant le champ ; dépendance manquante → erreur nommée ; `enabled: false` respecté.
- Commits par chemin uniquement ; `dispose()` en dernier ; traces `// AS3:` gardées sur ce qui est déplacé.

## Décisions

- **D1 — Contenu du paquet.**
  - `core/runtime/**` va dans `packages/ambreia-kernel/src/runtime/` : `Component`, `ComponentContext`, `CoreComponentContext`, `ComponentDependency`, `IID`, `IContext`, les événements et les exceptions. `core/Core.ts` va dans `src/Core.ts`.
  - Seuls les IID qui ne nomment pas de type du jeu suivent : `IID_Core` et `IID_AssetLibrary`. Les autres restent au moteur (futur `game`), car le kernel n'importe pas le jeu.
  - Les enveloppes DI de `core/` (`CoreCommunicationManager`, `core/localization`, `core/assets`) restent au moteur pour J5.
- **D2 — Schéma.**

  ```ts
  // @ambreia/kernel/config/AppConfig.ts
  export const AppSection = z.object({
      server: z.object({host: z.string().min(1), ports: z.array(z.number().int().positive()).default([40001])}),
      sso: z.string().optional(),          // ?sso=
      startLink: z.string().optional(),    // ?link=
      configurationUrl: z.string().optional()
  });
  // la config complète : { app, legacy: Record<string,string>, <feature id>: {enabled: boolean, ...son schéma} }
  ```

  Le défaut de `app.server.host` reprend la règle d'`index.html` : la page servie depuis `localhost`/`127.0.0.1` vise l'hôte de dev, sinon `ws(s)://<origine>/ws`. Il est calculé par la fonction de sources navigateur, pas dans le schéma, qui reste pur.
- **D3 — `legacy`.** `config.json.legacy` (objet `clé: valeur`) remplace `IVortexConfig.configuration` et les clés texte de premier niveau. Le `HabboConfigurationManager` les applique après son téléchargement, au même endroit qu'aujourd'hui. Les clés réservées (`reservedKeys`) disparaissent. `startLink`, qui s'y glissait par erreur, devient `app.startLink`.
- **D4 — Features.**

  ```ts
  export interface IFeatureContext<C> { readonly context: IContext; readonly config: Readonly<C>; readonly app: Readonly<AppConfig> }
  export interface IFeature<C = Record<string, never>>
  {
      readonly id: string;
      readonly config?: z.ZodType<C>;               // sa section, sans `enabled` (ajouté par le kernel)
      readonly provides?: readonly IID<any>[];
      create(ctx: IFeatureContext<C>): Promise<FeatureProduct> | FeatureProduct;
  }
  export type FeatureProduct = Component | {instance: unknown; attach?: IAttachInstanceOptions} | null;
  export function defineFeature<C>(feature: IFeature<C>): IFeature<C>;
  ```

  - Ce dont une feature dépend, le kernel le lit sur ce qu'elle a créé : les `ComponentDependency` obligatoires d'un `Component`, ou `attach.dependencies` d'une instance. On ne le déclare pas deux fois.
- **D5 — Démarrage.**

  ```ts
  export async function bootFeatures(context: CoreComponentContext, features: readonly IFeature<any>[], config: IKernelConfig): Promise<IKernelReport>
  ```

  1. Les features désactivées sont sautées.
  2. Les autres sont créées dans l'ordre de la liste. Un `create` asynchrone est attendu : la configuration télécharge avant les suivantes, comme aujourd'hui.
  3. Ce qui est créé est attaché sous `provides`.
  4. Puis, avant tout `initialize`, le kernel vérifie chaque dépendance obligatoire : il faut un fournisseur parmi les `provides` actifs ou les interfaces enregistrées par l'hôte (`IID_Core`, `IID_AssetLibrary`, `IID_CoreCommunicationManager`). Sinon, `FeatureDependencyError` : « la feature *room-ui* attend *IID_RoomEngine* », complété par « que fournit *room-engine*, désactivée » quand c'est le cas.

  `IKernelReport` (l'introspection) liste, pour chaque feature :
  - `id`, `enabled` ;
  - `provides` et `requires` (noms d'IID) ;
  - `state` : `disabled`, `locked` ou `ready`, relu en direct.

  `window.__ambreia.kernel` l'expose en dev.
- **D6 — Démarrage identique, mesuré.** Avant tout changement de `prepareCore`, une empreinte du démarrage est prise sur le client en dev, par le pilote :
  - l'ordre des IID enregistrés ;
  - les composants verrouillés après 6 s ;
  - toutes les propriétés de configuration (`HabboConfigurationManager._properties`, triées) ;
  - les étapes de la barre de chargement.

  Elle est comparée après la tâche 4. Un hook de dev temporaire (`window.__ambreia.boot`) la fournit ; il reste, documenté, comme base de l'introspection.

## Review Focus

1. **Une propriété de configuration change de valeur ou disparaît** après le passage à `config.json`/`legacy` (ordre de fusion, clé réservée qui fuyait, `startLink`) → une URL d'asset vide, rien ne s'affiche. Attendu : toutes les propriétés identiques. Pin : Task 4, empreinte avant/après (D6).
2. **L'ordre d'attache change** (feature asynchrone non attendue, `create` qui attache trop tôt) → la session ou le RoomEngine reçoivent leurs dépendances dans un autre ordre, ou restent verrouillés. Pin : Task 4, empreinte des IID et des verrouillés.
3. **Une feature désactivée laisse un dépendant optionnel en vie mais cassé** (dépendance optionnelle `null`). Attendu : démarrage normal sans elle. Pin : Task 3, test « dépendance optionnelle d'une feature désactivée ».
4. **`config.json` absent (404) ou JSON invalide** → aujourd'hui rien, demain écran d'erreur à tort ou crash. Attendu : absent = défauts ; illisible = erreur nommée « config.json : … ». Pin : Task 2, tests.
5. **Glaze et l'imager**, qui démarrent un `Core` à la main, cassent avec le déplacement. Pin : Task 1, `pnpm check` et leurs builds, plus le démarrage de Glaze.

### Task 3 : Les features

**Files :** `packages/ambreia-kernel/src/feature/{defineFeature,bootFeatures,FeatureDependencyError,KernelReport}.ts` ; test `packages/ambreia-kernel/test/features.test.ts`.

**Consumes :** `IKernelConfig` (Task 2), `ComponentContext.attachComponent/attachInstance` (Task 1).
**Produces :** l'API de D4 et D5.

- [ ] Tests (rouges), avec de petits `Component` de test :
  - (a) deux features, B dépend obligatoirement de l'IID de A → les deux `ready` après `context.initialize()` ;
  - (b) B seule → `FeatureDependencyError` « feature "b" waits on IID_A, which no enabled feature provides », levée avant `initialize()` ;
  - (c) A désactivée → même erreur, complétée de « (provided by "a", disabled) » ;

  - (f) une feature qui rend `{instance, attach}` est enregistrée par `attachInstance` ;
  - (g) le rapport donne `provides`/`requires` en noms d'IID.
- [ ] Implémenter (vert). `requires` se lit sur les `ComponentDependency` du composant créé ; il faut pour cela un accès en lecture, `Component.requiredDependencies` (TS-only). Pour une instance, on lit `attach.dependencies`.
