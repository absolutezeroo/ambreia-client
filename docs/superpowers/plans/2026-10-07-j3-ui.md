# J3 — `@ambreia/ui` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** sortir le système de fenêtres du moteur en un paquet autonome `@ambreia/ui` (moteur de
fenêtres, layouts XML, skins, thèmes, dialogues et widgets génériques, registre de widgets), qu'un bac
à sable et Glaze utilisent sans le moteur.

**Architecture :** `core/window` (262 fichiers) devient le cœur du paquet après avoir coupé ses trois
liens au moteur (suivi de liens, localisation, `DOMParser`). La partie générique de `habbo/window` le
rejoint. `HabboWindowManager` est coupé en deux : un `WindowManager` simple dans `ui` (contextes,
layouts, dialogues, rendu, assets, indices, widgets, sa propre boucle de mise à jour et ses propres
events) et un `HabboWindowManager` du moteur qui l'étend avec les services du jeu. Le DI l'enregistre
par `attachInstance`, étendu pour porter des dépendances et une mise à jour. Les widgets passent par un
`WidgetRegistry` : `ui` enregistre les siens, le moteur les widgets de jeu. Glaze démarre sur `ui` seul.

**Tech Stack :** TypeScript 5, Canvas 2D (le système de fenêtres ne dépend pas de PixiJS), Vite
(bac à sable), `node:test` + `tsx`, codemod `move-modules.mjs`.

**Spec :** `docs/superpowers/specs/2026-10-07-client-architecture-design.md` (§3 règle 1, §9 J3,
§11 test propre de J3, §12 décision n° 3).

## Global Constraints

- « À la fin de chaque jalon, le client compile, démarre et on entre dans une room. » (§9)
- « Les moteurs n'utilisent pas le DI : classes à constructeur simple, dépendances passées en
  paramètre (fournisseur d'assets, options typées, résolveur de textes, fabriques de canvas et de
  parser XML). `game` les enveloppe en composants. » (§3 règle 1)
- J3 : « `core/window` + partie générique de `habbo/window` ; registre de widgets ; widgets de jeu
  enregistrés depuis `game` ». Preuve : « Bac à sable `ui` qui affiche un layout ; Glaze ne dépend plus
  que de `ui` ». (§9)
- J3 test propre : « Le bac à sable `ui` charge un layout `vortex_*` et un layout Habbo ». (§11)
- Portée `@ambreia/`, dossier `packages/ambreia-ui`. **Ne pas confondre avec l'alias `@ui/*`** (= `src/`
  du client et de Glaze) : le paquet s'importe toujours `@ambreia/ui/...`.
- Déplacements par `move-modules.mjs` (simulation sans violation avant `--apply`) ; commit par chemins
  explicites ; `pnpm check` vert avant chaque commit.

## Décisions prises par ce plan

| # | Décision | Pourquoi |
|---|---|---|
| D1 | Frontière générique / jeu de `habbo/window` (§12 n° 3) : est **jeu** tout fichier qui dépend de `room`, `avatar`, `session`, `communication`, `configuration`, d'un IID ou de `HabboWebTools` ; le reste est **générique** | Cartographie du 2026-10-07 ; la liste exacte est en Task 3 et Task 5. |
| D2 | `WindowManager` (ui) **est étendu** par `HabboWindowManager` (moteur), qui n'est plus un `Component` | 54 membres d'interface : une enveloppe par délégation serait de la recopie. `attachInstance` (J2) enregistre l'objet ; on lui ajoute les dépendances et la mise à jour (Task 1). |
| D3 | `ui` garde sa propre liste de receveurs de mise à jour et ses propres `events` | Les widgets génériques (`Countdown`, `RunningNumber`…) s'abonnent au gestionnaire, pas au contexte DI. |
| D4 | Le système de fenêtres reste un système **de navigateur** : `OffscreenCanvas`, les champs de saisie DOM, le curseur, `requestAnimationFrame` restent tels quels ; seul `DOMParser` passe par `platform()` | La preuve de J3 est un bac à sable dans un navigateur ; rendre les fenêtres sous Node n'est demandé par aucun jalon (YAGNI). |
| D5 | Le suivi de liens devient un rappel `onLink?(href)` du contexte ; la localisation une interface `IWindowLocalization` de `ui`, que le gestionnaire de localisation du moteur satisfait par sa forme | Le tableau de suiveurs du contexte n'est jamais rempli aujourd'hui ; les noms des méthodes de localisation sont ceux que `WindowContext` appelle déjà. |

## Review Focus

1. **Un consommateur reçoit le porteur DI au lieu du gestionnaire de fenêtres**, ou le reçoit avant que
   ses dépendances (localisation, configuration…) soient là → les fenêtres s'ouvrent sans texte ou
   plantent. Attendu : comme avant. Pin : Task 1, test « an instance with dependencies is announced
   only once they resolve » ; Task 8, parcours en direct.
2. **Un widget de jeu n'est plus créé** (registre non rempli, ou rempli après la construction d'un
   layout qui l'utilise) → emplacement vide. Attendu : chaque type de la liste actuelle se crée. Pin :
   Task 6, test qui compare les types enregistrés à la liste d'aujourd'hui.
3. **La boucle de mise à jour saute ou double** (le gestionnaire mis à jour par le contexte et par
   sa propre liste) → animations deux fois plus rapides ou figées. Pin : Task 4, le gestionnaire n'est
   inscrit qu'une fois (test), et Task 8 en direct.
4. **Glaze ne démarre plus** (il dépendait de `Core`, du DI et de stubs). Pin : Task 7, `pnpm --filter
   vortex-glaze build` et ouverture d'un layout dans Glaze avec le driver.
5. **Le rechargement de dev ralentit**. Pin : Task 8, mesure contre J2 (297 ms).

### Task 1 : `attachInstance` porte des dépendances et une mise à jour

**Files :** `packages/vortex-engine/src/core/runtime/ComponentContext.ts`, `IContext.ts` ; test
`packages/vortex-engine/test/attach-instance.test.ts` (ajouts).

**Interface :**

```ts
attachInstance<T>(iid: IID<T>, instance: T, options?: {
    /** Resolved before the instance is announced, like a Component's own dependencies. */
    dependencies?: ComponentDependency<any>[];
    /** Called every frame through the context's update loop. */
    update?: (deltaTime: number) => void;
    updatePriority?: number;
}): void
```

Implémentation : le porteur devient une sous-classe anonyme de `Component` dont le getter
`dependencies` renvoie la liste capturée en fermeture (le constructeur de `Component` la lit avant
l'initialisation des champs) ; si `update` est donné, le porteur s'inscrit par `registerUpdateReceiver`
une fois déverrouillé et transmet `update(dt)`.

- [ ] Tests d'abord (RED), puis implémentation (GREEN) :
  - « an instance with dependencies is announced only once they resolve » : une demande en attente sur
    `IID_Thing` ne reçoit rien tant que `IID_Dep` n'est pas attaché, puis reçoit l'instance (et le
    setter de la dépendance a reçu la sienne).
  - « the update option is called by the context's update loop, once per frame » : deux `update(16)`
    du contexte → deux appels.
- [ ] `pnpm check` vert ; commit `j3: attachInstance porte des dépendances et une mise à jour`.

### Task 4 : `WindowManager` (ui) et `HabboWindowManager` (moteur)

**Files :** nouveaux `packages/ambreia-ui/src/kit/WindowManager.ts`, `IWindowManager.ts`,
`IWindowManagerOptions.ts` ; `habbo/window/HabboWindowManager.ts`, `IHabboWindowManager.ts` ;

**Interfaces :**

```ts
export interface IWindowManagerOptions
{
    /** Resolves `${key}` texts; null leaves them as written. */
    localization: IWindowLocalization | null;
    /** `${...}` expansion for asset URLs (the hotel configuration in the client). */
    interpolate(text: string): string;
```

`displayFloorPlanEditor`, `toggleFullScreen`), plus `readonly events: EventEmitter` et
`update(deltaTime: number): void`. `IHabboWindowManager extends IWindowManager` et ne garde que les
membres de jeu.
