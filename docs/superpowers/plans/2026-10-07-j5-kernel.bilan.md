## Configuration (spec §5)

- **Sources.** Elles sont chargées une fois, avant tout, dans cet ordre :
  - défauts calculés depuis la page (l'hôte de dev sur `localhost`, `ws(s)://<origine>/ws` ailleurs) ;
  - `config.json` du déploiement (`public/config.example.json`) ;
  - `?sso=` et `?link=`.
- **Validation.** Le schéma est validé par Zod, puis le résultat est figé en profondeur. Une config invalide affiche un écran qui liste chaque champ fautif ; une section inconnue n'est qu'un avertissement.
- **`legacy`.** Les propriétés `clé: valeur` sont appliquées par le `HabboConfigurationManager` après son téléchargement d'`external_variables`, qui reste en place. Les ~270 `getProperty` continuent de marcher. C'est l'adaptateur de migration du §5.
- **Disparus :**
  - `IVortexConfig.connection`, `configuration`, `configurationUrl` et `startLink` ;
  - l'index de chaîne de premier niveau, et sa liste de clés réservées (`startLink` fuyait par elle en propriété) ;
  - le calcul d'`index.html`.

## Features (spec §4)

- **Déclaration.** Une feature fournit `id` (aussi le nom de sa section), `config`, `provides`, `create`, et `afterAttach` (attendu avant la feature suivante : c'est là que la configuration télécharge).
- **Dépendances.** Elles se lisent sur ce que la feature a créé : les dépendances obligatoires d'un `Component`, ou celles de l'attache d'une instance.
- **Démarrage.**
  - `bootFeatures` crée les features actives dans l'ordre de la liste, puis vérifie chaque dépendance obligatoire.
  - Il lève `FeatureDependencyError` en nommant la feature et l'interface, et le cas échéant la feature désactivée qui l'aurait fournie.
  - Aujourd'hui, le DI laissait le composant verrouillé en silence.
- **Introspection.** En dev, `window.__ambreia.kernel()` donne l'id, ce qui est fourni, ce qui est attendu et l'état lu en direct. `window.__ambreia.boot()` donne l'empreinte du démarrage.

## Preuve (§9, §11)

- **Démarrage identique**, mesuré par l'empreinte avant/après du même client en dev :
  - même ordre d'attache (14 composants) ;
  - aucun composant verrouillé ;
  - les 766 propriétés de configuration égales ;
  - les mêmes étapes de chargement ;
  - les 12 features `ready`.
- **Écrans d'erreur** (`.claude/skills/run-vortex-client/shots/j5-*.png`) :
  - `config.json` avec `app.server.ports: "x"` → « app.server.ports: Invalid input: expected array, received string » ;
  - `{"room-engine": {"enabled": false}}` → « Feature "room-session" waits on IRoomEngine… (provided by "room-engine", disabled) », et de même pour `room-ui`.
- **Tests :**
  - `config` 9/9 : sources, priorité, erreur nommée, section inconnue, `enabled`, `legacy`, gel, sources navigateur, JSON illisible ;
  - `features` 8/8 : dépendance satisfaite, manquante, désactivée, optionnelle d'une désactivée, `create` asynchrone, instance, rapport, hôte et `afterAttach` ;
  - frontières 19/19 (mur du kernel ; les moteurs ne l'importent pas).
  - `pnpm check` vert ; builds du client, de l'imager et de Glaze ; Glaze identique au pixel près.
- **Rechargement de dev** : médiane 187 ms sur 16 mesures, sur la page avec ticket. Sans ticket, la page redirige et la mesure tombe pendant la navigation. La méthode diffère donc de J4 (278 ms).

## Écarts au plan

- Au kernel s'ajoutent `host`, passé à `create`, et `afterAttach`. `ENGINE_FEATURES` reste ainsi une liste constante, et les objets de l'hôte (assets, fichiers embarqués, `legacy`) n'y sont pas.
- L'éditeur d'avatar n'est pas une feature : le client le construit après ses layouts.
- Les barrels `core/` et `core/runtime/` du moteur réexportent le kernel.
- `config.json` n'est lu que si la réponse est du JSON : le serveur de dev répond `index.html` pour un fichier absent.
- `ComponentDependency` est obligatoire par défaut : un composant qui lit un champ de constructeur dans `dependencies` (lu pendant `super()`) rend sa dépendance obligatoire sans le vouloir.
